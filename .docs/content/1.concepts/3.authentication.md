# Authentication and Authorization

ArmoniK decides who may do what with **grants**. It holds no account, no password and no copy of your
directory: a caller proves who they are with a credential issued elsewhere, and the grants of the cluster
say what that caller may do. Authorization is disabled by default, in which case every request is allowed.

## Identifying the caller

A caller presents **either** a token from an OpenID Connect identity provider **or** a client certificate,
never both: a request carrying both is refused as unauthenticated. ArmoniK derives **principals** from the
credential:

| Credential         | Caller                                  | Roles                                                 |
|--------------------|-----------------------------------------|-------------------------------------------------------|
| Token              | `oid:<value of Identity:SubjectClaim>`  | `role:<value>` for each value of `Identity:RolesClaim` |
| Client certificate | `cn:<common name>`                      | `role:<unit>` for each organizational unit (OU)       |

A role is the same principal whichever credential carries it: `role:modelling-team` assigned in the identity
provider and `OU=modelling-team` written into a certificate are one and the same. Certificates must
therefore be issued with the care role assignments deserve: whoever can have a certificate issued with any
organizational unit obtains the corresponding role, `cluster-admin` holders included. Use a client
certificate authority dedicated to ArmoniK.

The prefix keeps identities apart: a certificate whose common name looks like a directory identifier is
`cn:`, never `oid:`. Comparisons are ordinal.

### Tokens

Tokens are validated in the control plane when `Identity:Authority` is set:

| Option                          | Default  | Meaning                                                                  |
|---------------------------------|----------|--------------------------------------------------------------------------|
| `Identity__Authority`           |          | OpenID Connect authority. Tokens are refused when empty                  |
| `Identity__Audience`            |          | Audience the token must be issued for. Required with an authority        |
| `Identity__TenantId`            |          | Tenant (`tid` claim) the token must be issued by, not checked when empty  |
| `Identity__SubjectClaim`        | `oid`    | Claim carrying an identifier stable across applications                  |
| `Identity__RolesClaim`          | `roles`  | Claim carrying the roles                                                 |
| `Identity__RequireHttpsMetadata`| `true`   | Whether the authority metadata must be fetched over HTTPS                |
| `Identity__MetadataRefreshInterval` | `00:00:30` | Delay before the authority metadata is read again after a failed read. Until it was read once, tokens are answered `Unavailable` and the Submitter is not ready |
| `Identity__ValidateTokens`      | `true`   | Whether tokens are validated. When `false`, their claims are taken as they are |

- **Entra ID**: declare one app role per team on the application, assign users or groups to it, and keep the
  defaults: `oid` is the immutable object identifier (`sub` is pairwise per application) and app roles are
  emitted in `roles`.
- **Keycloak**: create one client role per team, add a *User Client Role* mapper writing them to a flat,
  multivalued `roles` claim and an *Audience* mapper for the client, and set `Identity__SubjectClaim=sub`.

Removing a role from somebody takes effect when their token is renewed.

A proxy authenticating callers by other means can write the token itself, with the subject and roles claims, and
the control plane can take it without validating it: set `Identity__ValidateTokens=false` and leave
`Identity__Authority` empty. Neither signature, issuer, audience nor lifetime is then checked, so **the control
plane must only be reachable through that proxy**: anyone else could write a token with any role.

### Client certificates

The ingress verifies the client certificate and forwards it in the `X-Forwarded-Client-Cert` header
(`Identity__CertificateHeader`), in the [format written by Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/headers#x-forwarded-client-cert),
text or JSON. The control plane reads the certificate from `Cert` and refuses the request when:

- the header holds more than one element: a proxy appending its element keeps the ones sent by the client,
  so the ingress verifying the certificate must replace the header;
- the element has no `Cert`, or a `Cert` that is not a single PEM certificate (`Chain` is not read);
- `Hash`, when present, is not the SHA-256 of the certificate;
- the header is malformed, or repeats `Cert` or `Hash` in the element.

The control plane does not validate the certificate again: **the control plane must only be reachable
through the ingress**, and listeners that do not verify a client certificate must drop this header, as the
provided nginx configuration does.

With Envoy, set on the listener verifying client certificates:

```yaml
forward_client_cert_details: SANITIZE_SET
set_current_client_cert_details:
  cert: true
```

With nginx, which writes no `Hash` since `$ssl_client_fingerprint` is SHA-1:

```nginx
grpc_set_header X-Forwarded-Client-Cert "Cert=\"$ssl_client_escaped_cert\"";
```

A proxy between the ingress and the control plane must forward the header unchanged (with Envoy,
`FORWARD_ONLY`, or `ALWAYS_FORWARD_ONLY` when that hop is not mTLS). A request carrying both a token and
this header is refused, so such a proxy must not add its own element either.

ArmoniK keeps no record of the certificates it accepts, so a certificate cannot be revoked in ArmoniK: revoke it at
the ingress, with a certificate revocation list or OCSP, or remove the grants naming its common name and the roles
of its organizational units.

## Grants

A grant gives a **permission set** to a **principal** under an optional **condition**. Grants only ever
allow: a right goes away when every grant conferring it is removed. A principal is `oid:…`, `cn:…`,
`role:…`, or `*` for every caller.

### Permissions

| Permission                | Action                                                         |
|---------------------------|----------------------------------------------------------------|
| `session:create`          | Create a session                                               |
| `session:read`            | View and list sessions                                         |
| `session:pause`           | Pause a session                                                |
| `session:resume`          | Resume a paused session                                        |
| `session:stop-submission` | Stop new tasks being submitted into a session                  |
| `session:cancel`          | Cancel a session and the tasks still to run                    |
| `session:close`           | Close a session                                                |
| `session:share`           | Add or remove a person in the session `sharedWith` list        |
| `session:delegate`        | Add or remove a person in the session `delegatedTo` list       |
| `session:transfer`        | Move the ownership of a session                                |
| `session:purge`           | Delete the data of a session                                   |
| `session:delete`          | Delete a session                                               |
| `task:read`               | View, list and count tasks                                     |
| `task:submit`             | Submit tasks                                                   |
| `task:cancel`             | Cancel tasks                                                   |
| `data:read`               | View and list results, never their content: their reference in the object storage (`opaque_id`) is left empty without `data:download` |
| `data:download`           | Download results                                               |
| `data:declare`            | Create the metadata of results                                 |
| `data:provide`            | Upload the data of results                                     |
| `data:import`             | Register the data of results from a reference                  |
| `data:delete`             | Delete the data of results                                     |
| `partition:read`          | View partitions                                                |
| `partition:create`        | Create partitions                                              |
| `partition:delete`        | Delete partitions                                              |
| `partition:modify`        | Change partitions                                              |
| `event:watch`             | Subscribe to the events of a session                           |
| `grant:read`              | View grants                                                    |
| `grant:manage`            | Create and revoke grants                                       |
| `permission-set:manage`   | Create, edit and delete permission sets                        |

Tasks and results are decided on the session holding them.

### Permission sets

No permission set is shipped with ArmoniK: the configuration defines every set its grants name, under any name, so
that the sets are governed by `ConfigRevision` like the grants. `*` stands for every permission of the catalogue. It
is stored as written and expanded when the set is read, so that versions with different catalogues store the same
set. A version reading a stored set that names a permission it does not know leaves out that permission only, and
records it in the audit.

The sets of the access model, to define in the configuration:

| Set                 | Permissions                                                                                                                                                                                                 |
|---------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `session-view`      | `session:read`, `task:read`, `data:read`, `data:download`, `event:watch`                                                                                                                                    |
| `session-create`    | `session:create`, `partition:read`                                                                                                                                                                          |
| `session-own`       | `session-view` and `task:submit`, `session:share`, `session:delegate`, `session:transfer`, `session:pause`, `session:resume`, `session:stop-submission`, `session:cancel`, `session:close`, `session:purge`, `session:delete`, `task:cancel`, `data:declare`, `data:provide`, `data:delete` |
| `session-supervise` | `session:read`, `session:pause`, `session:resume`, `session:stop-submission`, `session:cancel`, `task:read`, `task:cancel`                                                                                  |
| `access-admin`      | `grant:read`, `grant:manage`, `permission-set:manage`                                                                                                                                                       |
| `cluster-admin`     | `*`                                                                                                                                                                                                         |

### Conditions

A condition is one of the forms below, or several of them joined with `&&`. No other form is accepted.

| Form                                       | Holds when                                                            |
|--------------------------------------------|-----------------------------------------------------------------------|
| `session.owner == request.caller`          | The caller is the owner of the session                                |
| `"P" in session.createdUnder`              | The session was created under the principal `P`                       |
| `grant.principal in session.createdUnder`  | The session was created under the principal of this grant             |
| `request.caller in session.sharedWith`     | The session is shared with the caller                                 |
| `request.caller in session.delegatedTo`    | The session is delegated to the caller                                |
| `request.partition == "Q"`                 | The request puts the partition `Q` in play                            |

A session records its owner (the caller who created it) and the principals it was created under: the
principal of **every** grant that conferred `session:create` on its declared partitions. Only session
creation and partition reads put a partition in play; creating a session is decided once per declared
partition, and refused as soon as one is not covered. The partition of its default task options (the default
partition when none is given) must be one of the declared ones, so that a session never runs tasks in a partition
its creation was not decided on.

A grant without condition applies everywhere. A grant that could never apply is refused when written: an
unknown set, a principal without prefix, a partition condition on a set without `session:create` nor
`partition:read`, a session condition on a set without any permission on sessions or on `session:create`, a
condition on administrative permissions, or two partitions in one condition. A grant for `*` testing `grant.principal in session.createdUnder` without a term
on the caller is refused too: it is the ownership condition without its owner term, and would give every
caller every session created under `*`. Written as `"*" in session.createdUnder`, the same reach is stated on
purpose, and is accepted.

### Example

```bash
# Create sessions in the research partition, and own the sessions created for the team
Authorization__Grants__0__Id=team-create
Authorization__Grants__0__Principal=role:modelling-team
Authorization__Grants__0__PermissionSet=session-create
Authorization__Grants__0__Condition=request.partition == "research"
Authorization__Grants__1__Id=team-own
Authorization__Grants__1__Principal=role:modelling-team
Authorization__Grants__1__PermissionSet=session-own
Authorization__Grants__1__Condition=session.owner == request.caller && grant.principal in session.createdUnder
# What sharing and delegation confer
Authorization__Grants__2__Id=share
Authorization__Grants__2__Principal=*
Authorization__Grants__2__PermissionSet=session-view
Authorization__Grants__2__Condition=request.caller in session.sharedWith
Authorization__Grants__3__Id=delegate
Authorization__Grants__3__Principal=*
Authorization__Grants__3__PermissionSet=session-own
Authorization__Grants__3__Condition=request.caller in session.delegatedTo
# The team lead follows and stops the work of the team
Authorization__Grants__4__Id=lead
Authorization__Grants__4__Principal=role:lead
Authorization__Grants__4__PermissionSet=session-supervise
Authorization__Grants__4__Condition="role:modelling-team" in session.createdUnder
# Platform administrators
Authorization__Grants__5__Id=platform
Authorization__Grants__5__Principal=role:platform-team
Authorization__Grants__5__PermissionSet=cluster-admin
# The sets named above: session-own, session-view and session-supervise are written the same way, from the table
Authorization__PermissionSets__0__Name=session-create
Authorization__PermissionSets__0__Permissions__0=session:create
Authorization__PermissionSets__0__Permissions__1=partition:read
Authorization__PermissionSets__1__Name=cluster-admin
Authorization__PermissionSets__1__Permissions__0=*
# A set of the deployment
Authorization__PermissionSets__2__Name=team-reader
Authorization__PermissionSets__2__Permissions__0=data:read
Authorization__PermissionSets__2__Permissions__1=data:download
```

Without the ownership grant, nobody may act on the sessions they create.

## Configuration

| Option                                  | Default    | Meaning                                                             |
|-----------------------------------------|------------|---------------------------------------------------------------------|
| `Authorization__Enabled`                | `false`    | Whether requests are authorized                                     |
| `Authorization__GrantCacheTtl`          | `00:00:10` | How long the stored grants are used before being read again: a revocation applies within twice that delay |
| `Authorization__ConfigRevision`         | `0`        | Revision of the grants of the configuration                         |
| `Authorization__Grants__N__*`           |            | Grants: `Id`, `Principal`, `PermissionSet`, optional `Condition`    |
| `Authorization__PermissionSets__N__*`   |            | Sets: `Name`, `Permissions__M`                                      |

The grants and sets of the configuration are validated at startup, which fails on any refused grant. The
process initializing the database (`InitServices__InitDatabase`, see [Initialization](./10.initialization.md))
then reconciles them with the storage, under a lock shared by the replicas:

- configured sets are written, a changed set getting a new version, past versions being kept;
- configured grants are created, changed or revoked;
- grants and sets written by the administration API are never changed;
- a configuration whose `ConfigRevision` is lower than the stored one changes nothing, so that a replica
  restarting with a previous configuration does not bring back a revoked grant: increase the revision with
  every change.

With PostgreSQL, the lock is an advisory lock held by a connection of the reconciling process, released when that
connection ends. A process whose host stops without closing it keeps the lock until the server notices that the
connection is gone; the `tcp_keepalives_idle`, `tcp_keepalives_interval` and `tcp_keepalives_count` settings of
the server bound that delay.

Decisions are taken on the stored grants, read again in the background once older than `GrantCacheTtl`,
requests being decided on the grants read last until the new read completes: a revoked grant stops applying
within twice that delay. When the storage cannot be read, the grants read last are used until they are twice
that old, then requests are answered `Unavailable` until the storage is back.
A reconciliation writes its grants and sets as one change, numbered by a generation: grants read while a
change is under way are not used, so that no decision is taken on a change half written. A change left
unfinished by a writer that failed is completed by the next reconciliation of the same `ConfigRevision` or a
later one. Until then every request is answered `Unavailable`, and a replica starting with an older revision
refuses to start, logging the revision required. Only the process initializing the database reconciles: the
other replicas never end the change, so run that process again to restore service.

With the provided deployment, `just authz=true keycloak=true deploy` enables authorization with grants for
the generated mTLS client certificate and the Keycloak role `modelling-team`; `runHtcmockMtls` and
`runHtcmockToken` run HtcMock with either credential.

## Decisions

A request is decided on the sessions its session, task and result identifiers resolve to, all of them:

| Situation                                                                   | Answer               |
|-----------------------------------------------------------------------------|----------------------|
| No credential, an invalid one, or both a token and a certificate            | `Unauthenticated`    |
| The caller may do nothing on the session: it is presented as absent         | `NotFound`           |
| The caller sees the session but lacks the permission                        | `PermissionDenied`   |
| A partition not covered when creating a session, for a caller holding grants | `PermissionDenied`  |
| Creating a session whose default task options use a partition it does not declare | `InvalidArgument` |
| The cluster holds no grant naming the caller or one of its roles, grants for `*` aside | `NotFound` |
| Authorization could not be decided, such as when the database is unreachable | `Unavailable`       |

- A caller is admitted when a grant names it or one of its roles: grants for `*` do not admit. A caller that
  holds only grants for `*` acts through them on sessions, but is answered `NotFound` by the methods that only
  require admission, `GetServiceConfiguration` and `CheckHealth`, which clients call when they start. To let
  every authenticated caller in, name them through a role their credentials carry.
- Identifiers of results or tasks belonging to another session than the one named by the request are
  refused as absent.
- Listings return only what the caller holds the permission on, and count only that.
- `GetCurrentUser` returns the caller, its roles followed by the sets it holds, and its permissions written
  `permission@cluster` or `permission@condition`; literals of conditions are only shown to callers holding
  `grant:read`. When authorization is disabled, it returns `Anonymous` holding every permission.

## Audit

Every decision writes a record under the `ArmoniK.Authorization.Audit` log category: the outcome (`Allow`,
`Forbidden`, `NotFound`, `Invalid`, `Unauthenticated` or `Fault`), the caller, the kind of credential, the service and
method, the permissions required, the sessions decided on, the reason of a refusal, and on an allow the grants
that conferred the permission with the version of their set. Changes to grants and sets made by the
reconciliation are recorded under the same category with the generation they belong to, and each replica
records the generation it decides on whenever it changes. ArmoniK does not route nor keep these records: collect
them out of reach of the people they are about.

## Known limitations

- Six methods of the legacy submitter are refused with `PermissionDenied` whatever the grants, the message
  naming the method to call instead: `CreateLargeTasks`, whose task dependencies arrive within the stream after
  the request is decided, and `CancelTasks`, `CountTasks`, `ListTasks`, `WaitForCompletion` and `ListSessions`,
  whose filters may name no session or several. See the
  [version migration](../0.installation/5.version-migration.md) for their replacements.
- Work already running is not stopped by a revocation: a task submitting further tasks is the continuation of
  authorized work, and workers are not restricted to the session of their task.
- Event streams are decided when they are opened.
- For a caller whose grants carry a condition, `ListTasks`, `ListTasksDetailed`, `CountTasksByStatus`,
  `ListResults` and `ListApplications` first read the id of every session the caller can see, then filter on
  that list: its cost grows with the number of those sessions, on every call. A filter requiring
  `session_id` to equal given values in every branch reads only those sessions; `ListApplications` always
  reads them all. With MongoDB, the list is sent in one query, which fails past about 350 000 sessions (the
  16 MiB limit of a command). Deleting finished sessions keeps it bounded.
- Partitions are only checked when a session is created.
- Sessions created while authorization was disabled have no owner, and are only reached by grants without
  `session.owner` term.
- Share, delegation and transfer are recorded on sessions, but the API writing them is not available yet,
  nor the administration API of grants and sets.
